# 场景 A–E 完整步骤

主文件 `SKILL.md` 只给场景索引。**真正动手时读这一份**，不要凭印象操作。

---

## 场景 A：收到体重秤照片 / 用户报体重

**触发**：用户发来秤面照片，或直接说「今早 145.2」「我刚称了 72.6 公斤」。

1. **读数**
   - 单位按 `config.yaml` 的 `weight_unit`（默认「斤」，1 斤 = 0.5 kg，脚本自动换算）。
   - 秤面同时显示体脂率 / BMI / 肌肉量时一并读出，但记住：**绝对值不可信，只作趋势参考**，不要拿体脂率下结论。
   - **看不清或不确定时，先问，不要猜。** 尤其小数点位置——读数错一次，趋势就被污染好几天。

2. **落库**

   ```bash
   "$PY" <PROJECT_ROOT>/scripts/record_body.py --weight <秤面读数> [--blob-id <附件指纹>] [--waist <cm>] [--note "<备注>"]
   ```

   - **不要传 `--photo`**。对话里的照片由宿主持有（临时路径），脚本一概不接触源文件；照片**不留档**。
   - `--blob-id` **可选**：宿主给了就带上（漏记对账用），没给就不传，**不要编一个值**。
   - 传来的是「今天的第一次」还是「补充」不影响：脚本按 (日期, source) 幂等，重复提交会更新而不是新增。
   - 腰围是**周频**指标，每周或每两周测一次即可。

3. **回报**：把「识别到什么 → 换算成什么 → 写入了什么」如实转述，让用户有机会当场纠错。例：
   > 秤面读数 145.2 斤 → 72.6 kg，已记入 10-26。体脂 21.3%（只作趋势参考，绝对值不必当真）。

**内置防线**：换算后 ≥100 kg 会被拒写（防「斤」当 kg）；超出 25–250 kg 一律拒写。被拒时说清是哪一种，不要绕过。

## 场景 B：收到餐食照片 / 用户口述吃了什么

**触发**：用户发来餐食照片；或说「午饭吃了食堂的青椒炒肉和一碗米饭」。

1. **取数，按这个优先级**
   - 用户口述的**菜名、份量、家里做的还是外食**——最可靠的输入，优先采信
   - 照片里的**菜品、餐具比例、拳头参照物**（用户拳宽见 `config.yaml`）
   - 用户说「少油 / 水煮 / 清蒸」要反映到区间里（往下压）

2. **必须给区间，不给点值**

   | 情形 | 区间宽窄 | 置信度 |
   |---|---|---|
   | 简单食物（一个蛋、一碗白饭） | 窄 | `high` |
   | 家常菜 | 中 | `mid` |
   | 外食 / 炒菜 / 带酱汁 | 宽 | `low` |

   **油量是最大误差源**：「低油」和「正常油」能差上百 kcal。

3. **落库**

   ```bash
   "$PY" <PROJECT_ROOT>/scripts/record_meal.py --meal-type lunch \
     --desc "家做西红柿炒蛋 + 米饭一碗 + 一拳青菜" --place 家 \
     --kcal-low <下限> --kcal-high <上限> \
     --protein-low <下限> --protein-high <上限> \
     --veg 1 --carb mid --confidence mid [--blob-id <附件指纹>]
   ```

   - 常吃的菜加 `--save-to-library` 存进份量库；下次用 `--from-library "<菜名>"` 复用。
     这是**让数据越用越准**的关键，比单张识别精度重要得多。第二次做同一道菜，主动提议用份量库。
   - **不要录膳食纤维**——照片判不出来。蔬菜用 `--veg`（拳数）这类定性指标代替。
   - `--meal-type` 取值：`breakfast` / `lunch` / `dinner` / `snack`。

4. **回报**：菜名 + 区间 + 置信度 + 当日累计。例：
   > 午餐已记：家做西红柿炒蛋 + 米饭一碗 + 一拳青菜，720–980 kcal（置信度中），蛋白 22–32 g。今天累计 1650–2300 kcal。

## 场景 C：出日报（定时触发 / 用户要求）

**完整顺序：① 搬运手环数据 → ② 漏记巡检（场景 D）→ ③ 出报告。** 前两步缺任一个，报告都可能是残的。

### 0. 先把手环数据搬进主库

```bash
"$PY" <PROJECT_ROOT>/scripts/sync_band.py --start <昨天> --end <今天>
```

- 手环组件拉来的数据躺在它自己的源库 `mi_fitness.db` 里，**不会自动进主库**，必须搬。**这是手环板块全空最常见的原因。**
- 幂等，重复跑安全；顺带把原始快照落 `data/raw/mi_fitness/`。
- 输出里出现「活动量异常偏大」之类的 ⚠️ → **如实转述**（可能是手机+手环同一天各自上报被累加）。
- 云端拉取失败不中断，会用源库现有数据继续 → 如实说明「本次未能联网拉取」。
- 用户没配手环 → 跳过这步，说明「活动 / 睡眠板块暂无数据」；用户想接但没接 → 转场景 E，**提示一次即可**，不反复推销。

### 1. 生成报告

```bash
"$PY" <PROJECT_ROOT>/scripts/build_report.py --date <昨天或指定日>
```

### 2. 补齐报告之外的上下文

```bash
"$PY" <PROJECT_ROOT>/scripts/record_body.py --show
"$PY" <PROJECT_ROOT>/scripts/record_meal.py --day <日期>
"$PY" <PROJECT_ROOT>/scripts/db_status.py
```

### 3. 讲给用户听

- **数据不足时如实说「数据不足」**，不要用估算填满报告。宁可报告短，不可报告假。
- **建议必须落在生活方式层面**，且**可执行到具体动作**——「晚饭后走 20 分钟」比「多运动」有用。
- 结论先行：先说一句总判断，再展开明细。

### 4. 展示 HTML

- 宿主有 `present_files`（WorkBuddy / 豆包都有）→ 用它打开报告。
- 没有这类工具 → 直接给报告的**绝对路径**，并说明「用浏览器打开」。

> 版式与判定口径（总览表、热量缺口、一句话总结）见 `references/report-format.md`。改报告前先读。

### 两个定时任务的差别

| | 22:00 当日速览 | 10:10 昨日完整日报 |
|---|---|---|
| 日期 | 今天 | 昨天 |
| 含睡眠 | ❌ 不查（当天还没睡完） | ✅ |
| 含趋势 | 简版 | 7 天趋势 + 周复盘 |
| 缺口口径 | 按区间算，明说「今天还没结束」 | 完整 |

## 场景 D：漏记巡检（每天出报告前先跑，用户也可随时喊）

**为什么有这一步**：照片不落盘、AI 直读附件——链路短，但**没有任何机制能保证每张都被处理过**。会话被岔开、窗口关掉、中断报错，都会让一张照片「到了但没录」，而库里看不出异常（只是少一条）。这一步就是对账。

```bash
"$PY" <PROJECT_ROOT>/scripts/audit_entries.py --date <昨天> --json
```

1. **看结论**：退出码 `0` = 无漏记，进场景 C；`2` = 有候选，先处置。
2. **有候选时**：
   - 候选条目会给出 `blob_path`（图还在本机）→ **直接读那张图识读，补录**，补录命令带上 `--blob-id`；
   - 明显不是健康数据的（工作截图等）→ `--dismiss <blob_id>` 标掉。
3. **把结果告诉用户**，一句话即可：「昨天你发的图里有 2 张没录上，我看了一下是午餐和晚餐，已经补进去了」。不要罗列过程，也不要因为「可能不是」就跳过不问——**宁可问一句，不可静默漏记**。

### ⚠️ 宿主边界（必须能如实说）

`audit_entries.py` 读的是 **WorkBuddy 的附件台账**（`~/.workbuddy/projects/*/*.jsonl` 里的 `image_blob_ref` + `~/.workbuddy/blobs/`）。

| 宿主 | 行为 |
|---|---|
| WorkBuddy | ✅ 真实对账 |
| 豆包等无该台账的宿主 | ⚠️ 输出「✅ 没有漏记」**或**「❌ 找不到会话记录目录」，**两种退出码都是 0** —— 假阴性，不是真的没漏 |

在后者上：
- **不得**向用户承诺「一张都没漏」；
- 改用**数据形态完整性**判断：某天有体重无餐食、三餐只录一餐、某数据源连续 2 天为 0 → 报告里标黄/标红，并说明「可能是没记，也可能是设备没同步」。

另有一种**任何宿主都查不到**的情况：消息压根没进到会话记录里（比如主机没开时手机端发的）。这种如实说「查不到」，别假装覆盖了。

**噪音规则**：文件名命中 `config.audit.ignore_name_patterns`（默认 `Clipboard_Screenshot*` / `Screen*` 等）的图视为例行非健康数据，只报一行计数。不要因此把候选当成完整清单——必要时加 `--include-screenshots`。

## 场景 E：接入小米云端取数（手环 / 体脂秤，可选增强）

**触发**：用户问「能不能同步手环数据」「装一下手环同步」；或 `config.yaml` 的 `sources.band.enabled` 非 true 且用户提到有小米设备。
**只提示一次，用户不接就翻篇**——这是可选增强，不是主线。

### 1. 一次说清能力与边界（别挤牙膏）

- **能拿到**：每日活动、逐分钟心率、睡眠分期、运动记录、血氧、压力；配了体脂秤另有身体成分
- 数据落在组件自己的源库 `mi_fitness.db`，**不会自动进主库**——出日报前的 `sync_band.py` 搬运永远少不了
- **这是第三方逆向项目**（mi-fitness-mcp-cn，MIT，非小米官方），接口可能因小米改版失效——失效时如实说，不装作没事
- 只读用户本人账号的数据；凭据存本机系统 keyring，不落明文
- **扫码登录那一步必须用户本人操作**，脚本只能旁边引导——提前说清，不承诺「全自动」

### 2. 询问是否安装，得到明确同意后才动手

```bash
"$PY" <SKILL_DIR>/scripts/install_band_mcp.py --root <PROJECT_ROOT>
```

- 包内**不含任何第三方源码**：安装器 `git clone --depth 1` 从上游拉，直连不通自动换代理镜像；pip 拉依赖仍需网络，国内慢就加 `--index-url https://pypi.tuna.tsinghua.edu.cn/simple`
- 默认带 Web 扫码仪表盘（`.[all]`）；想最小安装加 `--no-extras`；重装加 `--force`；先看计划加 `--dry-run`

### 3. 引导登录（二选一，推荐 A；必须用户本人操作）

- **A. 扫码（推荐）**：两个终端分别跑 `mi-fitness-mcp api` 和 `mi-fitness-mcp web` → 浏览器开 `http://127.0.0.1:8322/` → 扫码 → 小米运动健康 App 确认
- **B. 手动**：浏览器登录 account.xiaomi.com，从 Cookie 取 `userId` / `passToken` → `mi-fitness-mcp setup --mode mi_fitness_cloud --user-id <userId> --pass-token <passToken> --region cn`

登录后跑 `mi-fitness-mcp doctor`：看「连接状态 ✅」和「数据库： <路径>」。**源库路径以 doctor 输出为准**——安装器打印的「预期路径」只是预览，不拿它落库。

### 4. 写 config（用户确认后）

把 doctor 显示的源库路径、安装器给出的 `mcp_exe` 填进 `config/config.yaml` 的 `sources.band`（`enabled: true`，`verified_at` 填当天）。**只改这一块，不碰用户其他配置。**

### 5. 验证

```bash
"$PY" <PROJECT_ROOT>/scripts/sync_band.py --days 3 --dry-run   # 先预演
"$PY" <PROJECT_ROOT>/scripts/sync_band.py --days 3             # 确认后实跑
```

### 6. 回报

装到哪、登录成没成、配置改了哪几行、首次搬了多少条——如实说。安装失败就把失败原因和兜底指引原样转述，不静默跳过。
