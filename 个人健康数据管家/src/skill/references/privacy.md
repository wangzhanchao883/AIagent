# 隐私纪律

> 这是硬约束，不是建议。用户把体重照片、餐食照片、腰围、体脂这些交进来，
> 是**高度敏感的个人健康信息**。以下每条都要当真。

## 一、照片：只取数，取完即止

| 规则 | 说明 |
|---|---|
| **只用于取数** | 除读出数字外，不做任何其他用途 |
| **不留档** | 不保存、不复制、不转发、不另存到项目目录 |
| **不传 `--photo`** | 对话里发来的照片由 WorkBuddy 附件机制持有（临时路径），**脚本一概不接触源文件** |
| **不删 WorkBuddy 的副本** | App 自身会在 `~/.workbuddy/blobs/` 留副本——那是 App 行为，且是漏记巡检的补录窗口，**不要去动它** |

## 二、数据存储

- 全部数据**只存本机** SQLite 库，**不进任何云同步目录**
  （OneDrive / 百度网盘 / iCloud 等同步目录会让"本地数据"变成"云端数据"，这是最容易踩的坑）
- 设备凭据存本机系统 keyring（Windows DPAPI / macOS Keychain），**不落明文、不外传**
- 报告输出在本地目录，不自动上传
- **不把用户的健康数据发送到任何第三方服务**

## 三、日志与台账里的 blob_id

录入台账（`intake_log.jsonl`）会记录照片的 `blob_id`（sha256）。
这是**指纹，不是照片本身**，用于漏记巡检对账——保留它是有价值的。

- 可以保留 blob_id
- **不要**在台账或报告里写入照片的可读路径、原始文件名（可能含个人信息，如 `微信图片_20260315_142233.jpg`）

## 四、首次建库时提醒用户

帮用户初始化项目时，**主动提醒**：

1. **项目目录放在哪** —— 提醒放在本地磁盘、**不要放云同步目录**
2. **config.yaml 含真实身体数据**（身高、年龄、目标体重）—— 不要分享给别人
3. **config.yaml 不要提交到公开 Git 仓库** —— 若要用 Git 管项目，建议：
   ```bash
   echo "config/config.yaml" >> .gitignore
   echo "data/" >> .gitignore
   echo "reports/" >> .gitignore
   ```
4. **导出 / 分享报告前扫一眼** —— 报告里有真实体重、腰围、饮食记录，给别人看之前自己过一遍

## 五、viking 记忆与跨会话沉淀

若把健康数据写进长期记忆或知识库：

- **事实 / 偏好**（如"用户单位用斤""偏好早上称重"）→ 可沉淀
- **具体身体数据**（体重、腰围、摄入量）→ **属事件级**，标注来源与日期，且要用户确认后再写
- **不把健康数据与第三方同步**（如云端记忆服务、共享知识库）

## 六、导出与第三方

- 用户要求导出 / 分享报告时：**先问给谁看**，并提醒里面有真实身体数据
- 绝不把用户数据放进公开仓库、公开链接、社媒
- 用户要求删除时：确认范围 → 备份 → 走系统回收站而非 `rm` → 小批次、可回滚

## 七、敏感信息清单（打包 / 分享专家包时必查）

上传专家市场前，务必扫描并替换以下内容：

- [ ] 本机绝对路径（`C:\Users\<用户名>\...`、用户项目目录）
- [ ] 作者真实姓名、账号名、邮箱、手机号
- [ ] **真实身体数据**（体重、腰围、摄入热量、蛋白克数）
- [ ] 时间线（"某人于某日几点做了什么"）
- [ ] 数据库文件、日志、报告文件（可能含真实数据）
- [ ] 设备凭据、token、cookie

配置模板应是**占位值**（`name: "你的名字"`、`height_cm: 172`、`weight_kg: 70.0`），
并在开头注明"复制为 config.yaml 后按自己情况改"。

## 八、红线

**不编造数据**——缺项就留空，"没数据"本身是有效信息。
把估算说成测量、把"查不到"说成"已覆盖"，都是严重的信任事故。
