# 发布说明 · 1.4.0

**一句话**：从「WorkBuddy 专用专家包」变成「WorkBuddy 和豆包都能装的同一份技能」。

---

## 一、为什么要改

1.3.0 是个标准的 WorkBuddy 专家包，结构是两层：

- `agents/health-data-steward.md`（305 行）——人设、场景 A–E、输出规范、安全红线，**「专家性」都在这里**
- `skills/health-data-steward/SKILL.md`（281 行）——只讲脚本怎么调

豆包只有**一层上传技能**的入口，只读 `SKILL.md`。所以直接把它上传到豆包，拿到的是「一个会调脚本的助手」，而不是「健康数据管家」——人设、输出规范、红线全丢了。

**1.4.0 的核心动作就是把这 305 行行为层搬进 `SKILL.md`**，然后把细节拆到 `references/` 里按需加载。

## 三、豆包侧的实际适配

先说结论：**豆包吃的是标准 Agent Skills 规范，结构跟本技能完全一致。**

依据（本机实测，非推测）：

- 豆包工作区里的官方技能目录是 `.skills/`（100+ 个），用户上传的技能落在 `.user_skills/`
- 官方技能结构 = `SKILL.md` + `scripts/*.py` + `references/` + `sub-skills/`
- 官方技能里直接以 `python xxx.py` 调用脚本 → **支持执行 Python**
- 官方技能里出现 `present_files` 这个工具名，和 WorkBuddy **一字不差** → 报告展示不用改

真实差异只有三处，都已在文档里处理：

| 差异 | 1.4.0 的处理 |
|---|---|
| 定时任务工具叫 `create_cron_job`（不是 `automation_update`） | `references/scheduling.md` 给了两套写法对照表 |
| 通常没有附件 sha256 | `--blob-id` 明确标为**可选**，没给就不传，不要编值 |
| 没有 `~/.workbuddy` 附件台账 | 漏记巡检标注为「在非 WorkBuddy 宿主上是假阴性」，且给出替代判断法（数据形态完整性） |

## 四、两个阻塞问题已修（不修则装完即坏）

这两个都不是「优化」，是**新用户必踩**，所以这次一并处理：

### 1. 全新安装后第一次记餐 100% 失败

- **现象**：`sqlite3.OperationalError: table meal has no column named calcium_mg_low`
- **原因**：`record_meal.py` 的 INSERT 写了 19 个字段（含 `calcium_mg_low/high`），但 `init_db.py` 的 `CREATE TABLE meal` 只有 18 列，`REQUIRED_COLUMNS` 里也没登记这两列，所以 `init_db.py` 补不上
- **为什么之前没暴露**：作者的库是历史演进出来的（20 列），发布版建表语句没跟上；已发布的两个用户大概只记过体重没记过餐
- **修复**：`init_db.py` 两处 —— 建表语句补两列 + `REQUIRED_COLUMNS["meal"]` 补两项（老库跑 `init_db.py` 即可幂等补上）

### 2. 目标体重单位错算，首个界面就说错话

- **现象**：按默认单位（斤）配置 `--target-weight 130`，记完体重显示「体重 145.2 / 目标 260.0 斤 已达成（低 114.8 斤）」
- **原因**：`bootstrap.py` 把 `--target-weight` 的原始值直接写进 `config` 的 `weight_kg`，没按 `--unit` 换算。130 斤被当成 130 kg，显示时再 ×2 = 260 斤
- **为什么影响面大**：**默认单位就是斤**，几乎所有新用户都会撞上，而且第一句话就自相矛盾
- **修复**：`bootstrap.py` 写入前按 `--unit` 换算成 kg；顺带修正了没给目标体重时的 BMI 反推公式（原 `22.5×身高/10`，171cm 会算出 38.5 kg；应为 `22.5×(身高/100)²` → 65.8 kg）

## 五、按你的意思**没有**修的两项（已写进文档，不装作没事）

### 1. `--root` 参数被模块导入吞掉

`_intake_log.py` 在模块顶层就调了根目录解析，那个函数会从 `sys.argv` 里删掉 `--root`。三个录入脚本先 `from _intake_log import ...`，等它们自己解析时已经找不到这个参数，于是静默回落到 `~/health-data`。

**1.4.0 的处理**：不改代码，改成**规定项目根固定 `~/health-data`**，要换位置用环境变量 `HEALTH_ROOT`。写进了 `SKILL.md` 第九节「已知限制」和故障排查表。

### 2. 漏记巡检在非 WorkBuddy 宿主上的假阴性

没有台账时脚本报「✅ 没有漏记」或「❌ 找不到会话记录目录」，**退出码都是 0**。Agent 靠退出码判断，会把环境问题读成「一切正常」。

**1.4.0 的处理**：不改代码，改成**在文档层明确标注这是已知限制**，并给出替代判断法（数据形态完整性：某天有体重无餐食、三餐只录一餐、某数据源连续 2 天为 0 → 报告标黄/标红）。同时在 `SKILL.md` 里写死一句：「这些宿主上不得向用户承诺『一张都没漏』」。

> 这两项都在 README 的「已知限制」里对用户公开，不藏。

## 七、产物与分发

发布包挂在 GitHub Release，不进仓库：

| 附件 | 给谁 | 大小 |
|---|---|---|
| `health-data-steward-workbuddy.zip` | WorkBuddy | 375 KB |
| `health-data-steward-doubao.zip` | 豆包 | 125 KB |

两者核心内容逐字节相同，差别只是 WorkBuddy 多一层专家包外壳。

**产物为什么不提交进仓库**：同一份 `SKILL.md` 若同时存在于源码和产物里，就成了两份副本——有人在网页上直接改产物、下次构建被静默覆盖，是很常见的漂移来源。版本号交给 git tag，成品交给 Release，仓库里只留一份源。

**改动方式**：改 `src/`，然后 `python build.py --ver 1.4.1`。构建脚本会把两个固定文件名的 zip 打到 `dist/`，再 `gh release create` 上传。**不要手改 `dist/` 里的东西**——下次构建会被整个覆盖。
